01

What is actually repeated

Measured, not assumed — every table name in every repo, intersected; every capability grep'd across all eight backends.

The sharpest evidence

  • 43 of 46 shadcn UI components are byte-identical between EntiqStart and Client Portal — the same files, copied.
  • Six separate users tables; five notifications; four audit_logs; three each of roles, templates, invitations, entities, document_requests, revoked_tokens.
  • Client Portal carries a 37-file second AML engine — its own orchestrator, OpenSanctions PEP, DFAT sanctions, ASIC screen, adverse media, country risk, source of funds, and its own Postgres store.
Corrections from this pass

GrowKyc has no e-signature capability. Its ~500 "signature" matches are webhook HMAC verification, not signing. E-Sign's Xero integration is an empty stub — one comment line; only its BAS (492 lines) and Client Portal (548 lines) adapters are real.

03

How a firm buys it

One registration, one login, then modules are switched on individually. This is the only part of the architecture that does not exist anywhere in the estate today — it has to be built, not moved.

Every module declares itself

The catalogue, the navigation, the permission list and the entitlement checks are all generated from one manifest per module — so adding a tenth module is a file, not a change to the platform.

modules/accounting/module.toml key = "accounting" name = "Accounting & Tax" sku = "acc-standard" requires = ["core"] # hard dependency — cannot run without enhances = ["esign", "kyc"] # optional — richer when present, upsell when not provides = ["ledger", "bas"] # capabilities other modules may consume permissions = ["acc:read", "acc:post", "acc:lodge"] nav = [{ label = "Workpapers", path = "/accounting/workpapers" }] [[panels]] # what it contributes to the FREE client record slot = "client.360" render = "AccountingSummary" upsell = "See ledger balance, open jobs and BAS due dates here" [pricing] model = "per_seat" # or "metered" — KYC per check, E-Sign per envelope meter = []

The CRM is a subscription like any other — it just happens to be the one that is required. Treat it as module crm in the same tenant_subscriptions table, with no special-case code. A trial is not a separate mechanism either: it is the same row with status = trialing and a trial_ends_at, so expiry is a status transition rather than a second code path. That uniformity means module trials come free later, without new plumbing.

The client record is therefore not a fixed page: it is a composition surface that paid modules contribute panels to, and the base plan is what every tenant always has.

Two pricing shapes, one ledger

Modules do not all price the same way, and the model has to carry both from the start. Accounting and Support are seat-priced; KYC is per verification (GrowKyc already prices at $70 a check) and E-Sign is per envelope. So an invoice is subscription lines plus metered lines.

The metering already exists: GrowKyc's billing_events is an append-only, hash-chained, tenant-scoped ledger with units, unit price, GST, Square payment linkage and a chain-verification endpoint. It needs one new dimension — module — and subscription lines alongside the metered ones. That is a small change to a solid foundation, not a new billing system.

What happens on day 16

A paid base plan needs an answer for non-payment, and in this product that answer is constrained by law rather than preference. Suspension must restrict access without destroying records.

The commercial mechanic that falls out of this

A module that another module enhances becomes an upsell surface. A firm with Accounting but not E-Sign sees "Send for signature" with an Add E-Sign prompt rather than a hidden feature or a broken button. Every cross-module link in the next section is therefore both an engineering dependency and a revenue path — which is why the interlinks are worth building properly.

Why this gets cheap in one codebase

Eight of these fourteen links already have one half written — a generic driver waiting for a base URL, or an adapter waiting for a caller. In separate repos, wiring them means deployment coordination, contract versioning and cross-repo releases. In one codebase they become an import and a function call.

07

The build plan

Three production systems and a store-reviewed mobile app stay live throughout. Nothing is rewritten; code moves, then de-duplicates. Each milestone ends in something you can demonstrate.

M0

Land the repos side by side

Monorepo created; all nine imported with history preserved (git subtree / filter-repo). Nothing merges. CI builds each as it stands. Module manifest format agreed and written for all nine. Consolidate GrowAccounting's six scattered copies first.
Demo: one checkout, one CI run, nine green builds.

M1

Extract the zero-risk packages

ui, storage, pdf, ratelimit, apikeys, webhooks. No domain logic, no data model, no migration — the safest possible first cut. The UI package alone deletes three duplicate copies of 46 components.
Demo: change a button once, see it change in four apps.

M2

The platform spine — identity, tenancy, subscriptions

The keystone, and the only net-new build. One login per person; one canonical tenant; tenant_subscriptions plus require_module(). Built from GrowKyc's fail-closed tenancy and E-Sign's principal binding. Two security gaps close here, not later.
Demo: sign up a firm, log in once, reach a tenant that owns nothing yet.

M3

The $99 CRM — it must earn the second payment in 15 days

Customer, entity, contact, relationship, timeline, tasks, notes, pipeline — promoted from GrowKyc's client and entity model, absorbing Accounting's ClientGroup hierarchy and Portal's Firm-Entity tree. Define the client.360 panel slots now, with every module's tile rendering as an upsell. Fix globally-unique users.email, which today makes one person belong to exactly one firm. Time-to-value is the whole game here: GrowKyc's existing CSV import already ingests a Xero or MYOB contacts export — make that the first screen after signup.
Demo: a firm signs up, imports 400 clients from Xero in two minutes, and is working before it has paid anything.

M4

Prove the paid mechanism on Training and Support

The two cheapest modules — 21 and 19 tables, no production coupling — move onto the spine, lose their own user tables, and fill their panel slots. Support's Prisma models convert to SQLAlchemy here rather than as a separate exercise. First real money through the subscription path.
Demo: buy Support from inside the free CRM; the empty tile fills with live tickets.

M5

KYC/AML and E-Sign onto the spine

The two modules every other module depends on. Delete Client Portal's 37-file AML engine and its signature endpoints once the real ones are reachable.
Demo: run a screening and send a document for signature from inside Accounting.

M6

Accounting, Client Portal, Start — and the interlinks

The expensive tier, and the payoff. Point Start's drivers at KYC/AML and E-Sign; point its stage-11 handover at the core. Delete Portal's second Xero client. Embed the Support widget in the Portal.
Demo: onboard a client end to end — intake, screening, signing, activation — across four modules, once.

M7

One shell, one API client, marketplace live

Single React app, route-scoped per module, navigation driven by entitlements. Flutter client regenerated once against the unified contract — one store-review cycle instead of one per change. Self-serve signup and module marketplace open.
Demo: a firm signs itself up and buys a second module without you touching anything.

08

Risks worth naming

  • Nine stacks must converge. FastAPI 0.104 → 0.141, three Postgres majors, plus two Node backends and one on DynamoDB. Lending (RequestIQ) is serverless on AWS with a different database paradigm — it joins the monorepo as source, but should keep its own runtime until there is a reason not to.
  • Two data-access layers — SQLAlchemy and Prisma. Support's 19 Prisma models are the smallest to convert; do it during its identity migration rather than as a separate exercise.
  • Client Portal has a second active developer and squashed history. Agree branching before its code moves.
  • Start changes daily. Import it late, or freeze a branch by agreement.
  • Two security gaps close during phase 02, not after: Client Portal's fail-open firm scoping, and RequestIQ's tenant read from a request parameter.
Still needed to finalise sequencing

Which modules are revenue-live today? Is Accounting or Client Portal the strategic centre of the accounting product? They are one product in two codebases. Is Lending in scope, given it is a different org, vertical and cloud?
